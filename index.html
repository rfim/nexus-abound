NEXUS

Every change in Aurora lands in the lake exactly once, and the lake is checked against the source row by row.

I'm Vim, R. Firman Insan Muhammad, a data engineer in London. For four years I've owned the data lake and pipelines behind risk and fraud models at Lifepal, a regulated insurance marketplace. That meant CDC from PostgreSQL and MySQL into S3 with AWS DMS and Debezium, Spark and Glue jobs that merge changes idempotently, and moving reporting and model training off the production database. This site is NEXUS, the platform I built at Lifepal, applied to data shaped like a consumer lender's: Aurora → DMS → Iceberg on S3. The data is synthetic, and everything runs from this repository.

01 · The pathwhat runs in this repo

Aurora to the lake. Proven, not assumed.

Five steps from a commit in the lending database to a table a data scientist can trust. Every number on this page comes from the last run of the Python in this repository.

01 · CAPTURE
DMS

A full load, then CDC. Each change carries Op, its commit time and AR_H_CHANGE_SEQ.

02 · LAND
Bronze

Changes are keyed by primary key and change sequence. Replaying every file changed – rows.

03 · APPLY
MERGE

The newest change sequence wins. Deletes become tombstones, so a late update can't bring a row back.

04 · PROVE
–/–

Silver is checked against the source row by row. The first check caught a gap in DMS's delivery.

05 · SERVE
Iceberg

Partitioned and sorted for Athena, and point in time for model calibration.

The stack, as the role lists it: Aurora PostgreSQL/MySQL → AWS DMS → S3 → Spark on Glue → Iceberg → Athena, with Lambda and ECS on Fargate around it. Locally the same PySpark runs against an Iceberg Hadoop catalog. On Glue 5.0 it uses the Glue Data Catalog (glue/cdc_job.py).
02 · Six CDC problemsplanted in the data, caught in the run

What DMS really delivers. And what it takes.

The generator runs a small lender forward for a year and writes what DMS would put in S3. It plants the six problems I've met running CDC in production. Each one is tested.

One repayment, change by change

A missed instalment is paid late in one transaction made of two statements, so both changes have the same commit timestamp. Ordering by cdc_ts would leave the payment amount to chance. change_seq orders them. The last row is the reload, which agrees.

05 · Speed, freshness and costbytes scanned is the Athena bill

Read only what you need. Pay only for that.

Athena charges $5 per TB scanned, and Spark's time goes the same way. Here the same two queries are planned on three layouts of the Open Banking transactions, using Iceberg's own file statistics. All three layouts return the same rows.

Partition

months(booked_at)

A hidden partition transform: queries filter on booked_at, never on a partition column, and the spec can evolve without a rewrite.

Sort

WRITE ORDERED BY customer_id, booked_at

Each file covers a narrow range of customers, so min/max bounds prune files for the per-customer reads that Data Science runs.

Maintain

rewrite_data_files · expire_snapshots

Compaction undoes the small files that MERGE and streaming leave behind. Expiry keeps metadata and storage small, and makes erasure real.

At this size, files are capped at 16 KB so that a month spans several sorted files, as it would at 128 MB in production. The ratios are what carry over, not the absolute bytes.

06 · For Data Sciencethe bridge the role describes

Calibrate on the lake. As of the decision.

Model calibration needs two things the production database can't give cheaply: what the score said at decision time, and what happened next. It also needs every feature as it was known then, not as it is today.

Predicted against observed, by score band

The share of loans that missed one of their first three instalments, per score band (gold.ds_calibration_by_band).

Point in time, or a leak

Open Banking enrichment relabels some salary credits days after the fetch. A feature built from today's labels sees income the model never saw at decision time. The point-in-time version joins the change history (silver.ob_transactions_history) as of decided_at.

At Lifepal I built the feature pipelines behind the customer-risk and claims-fraud models (LightGBM, XGBoost): point-in-time training sets, training/serving parity, drift monitoring and recalibration. The tables here have the same shape: one row per decision, the score as stored, the outcome as observed.

07 · On AWSthe same code, deployed

DMS, Glue, Iceberg. As code.

The repository has everything needed to run this on AWS, written but not applied, since there's no AWS account behind a portfolio. Each file is short enough to read in an interview.

Capture

infra/dms/

S3 target settings: CSV with a header, TimestampColumnName=cdc_ts, Op on full load too, and the AR_H_CHANGE_SEQ header mapped to change_seq by a transformation rule.

Apply

glue/cdc_job.py

A Glue 5.0 job (Spark 3.5, Iceberg 1.7) that configures glue_catalog and runs the same bronze and silver functions, followed by the checks.

Provision

infra/terraform/

The DMS endpoints and task, the S3 bucket, the Glue database and job, and the IAM roles, all with least-privilege policies.

Around the pipeline: Lambda and ECS on Fargate

At Lifepal I ran services on Lambda and ECS. Here is where they'd sit in this pipeline. This is the design; the repository's code is the Spark part.

Event-driven · AWS Lambda

Small, short jobs on events

  • On S3 ObjectCreated from DMS: record the file and its arrival time, the file log bronze reads
  • On a failed check: post the incident with its failing keys to on-call
  • Every hour: compare change volume per table with its usual level, the alert that would have caught the 20 September gap
Containers · ECS on Fargate

Longer jobs, with no servers to run

  • The nightly reconciliation export from an Aurora read replica, so checks never load the writer
  • Ad-hoc backfills and table reloads, run as one-off Fargate tasks from the same image
  • A small internal API serving gold tables to Data Science tools, behind an ALB
