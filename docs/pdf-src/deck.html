04 · Land · PySpark on Iceberg

Safe re-runs: bronze keyed on the change

Every DMS file can arrive twice, late or out of order. Bronze keeps one row per change, so a re-run or a re-send changes nothing.

ingest(ingest(B, F), F) = ingest(B, F) · identity = (key, change_seq)
src/nexus/bronze.pyPySpark · Iceberg 1.7
def ingest(spark: SparkSession, src: dict, files: list[Path], batch_id: int) -> dict:
    name, pk = bronze_name(src), src["primary_key"]
    log = table("ops", "ingested_files")
    if not files:
        return {"files": 0, "rows_read": 0, "new_changes": 0, "duplicates": 0, "columns_added": []}
    df = (read_files(spark, files)
          .withColumn("cdc_ts", F.to_timestamp("cdc_ts"))
          .withColumn("_batch_id", F.lit(batch_id))
          .withColumn("_ingested_at", F.current_timestamp()))
    rows_read = df.count()
    # one copy of each change inside the batch; MERGE then skips any copy bronze already has
    w = Window.partitionBy(*pk, "change_seq").orderBy("_source_file")
    df = df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")

    if not spark.catalog.tableExists(name):
        df.limit(0).writeTo(name).using("iceberg").partitionedBy(F.days("cdc_ts")) \
            .tableProperty("format-version", "2").create()
    added = _evolve(spark, name, df)
    before = spark.table(name).count()
    df.createOrReplaceTempView("batch")
    on = " AND ".join(f"t.`{k}` = s.`{k}`" for k in pk + ["change_seq"])
    spark.sql(f"MERGE INTO {name} t USING batch s ON {on} WHEN NOT MATCHED THEN INSERT *")
    new = spark.table(name).count() - before

The guarantee

Each change is identified by its primary key and AR_H_CHANGE_SEQ, which DMS makes unique and increasing. A file name is not an identity: after a restart DMS re-sends the same changes in a new file.

At-least-once delivery from DMS becomes an exactly-once effect on the table.

At Lifepal

CDC from PostgreSQL and MySQL with DMS and with Kafka + Debezium, merged idempotently by Spark and Glue jobs. Reporting latency fell from 24 hours to under 5 minutes.

In the run

DMS re-sent 14 changes after a restart: skipped. Replaying every file DMS ever wrote, 57,025 changes, added 0 rows.

A column added mid-stream (apr_bps) becomes ALTER TABLE ADD COLUMNS: metadata only, no rewrite.

04 · Apply · PySpark on Iceberg

The newest change wins. Deletes stay deleted.

Silver holds the current state of every Aurora table. Three rules make it right whatever order the changes arrive in.

src/nexus/silver.pyPySpark · Iceberg MERGE
def latest(df: DataFrame, src: dict) -> DataFrame:
    w = Window.partitionBy(*src["primary_key"]).orderBy(F.col("change_seq").desc())
    df = df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")
    deleted = F.col("Op") == "D"
    keep = set(src["primary_key"])
    return df.select(*[F.col(c) if c in keep else F.when(deleted, F.lit(None)).otherwise(F.col(c)).alias(c)
                       for c in src["columns"]],
                     deleted.alias("is_deleted"), "cdc_ts", "change_seq")

    on = " AND ".join(f"t.`{k}` = s.`{k}`" for k in src["primary_key"])
    by_source = (" WHEN NOT MATCHED BY SOURCE AND NOT t.is_deleted THEN UPDATE SET t.is_deleted = true"
                 if authoritative else "")
    spark.sql(f"""MERGE INTO {name} t USING silver_batch s ON {on}
                  WHEN MATCHED AND s.change_seq > t.change_seq THEN UPDATE SET *
                  WHEN NOT MATCHED THEN INSERT *{by_source}""")

Three rules

change_seq decides. Two statements in one transaction share a cdc_ts; only the sequence orders them.

Deletes are tombstones that keep their change_seq, so an older update arriving late can't resurrect the row. Non-key values are nulled: erasure means erasure.

A reload is authoritative: WHEN NOT MATCHED BY SOURCE tombstones what the source no longer has.

In the run

53 two-statement transactions ordered correctly; C00016's late update arrived after the delete and left 0 live rows.

05 · Proving the lake

A check failed. The run fixed it.

No key can catch a row that never arrived. Only a comparison with the source can.

16 repayments rows didn't match Aurora

DMS delivered no repayments changes between 03:00 and 04:00 on 2026-09-20, the hour of the daily direct-debit run. The source has them, so the task resumed from the wrong position after an interruption: the rows are missing, not late.

Bronze had 0 changes in that hour, against a median of 10 on other days.

Fix: Reload repayments from the source (DMS 'reload table'), apply it as authoritative, re-run the reconciliation. Then alert on hourly change volume per table so a gap pages before a month-end report finds it.
src/nexus/silver.pya reload is authoritative
MERGE INTO lake.silver.repayments t
USING silver_batch s ON t.repayment_id = s.repayment_id
WHEN MATCHED AND s.change_seq > t.change_seq
  THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE AND NOT t.is_deleted
  THEN UPDATE SET t.is_deleted = true

After the reload: 18/18 checks pass, including reconciliation on every table.

05 · Prove · PySpark

Reconciliation: the check no key can replace

Silver against the source's own rows, on every contract column. It finds what a CDC stream can't tell you: the changes that never came.

src/nexus/checks.pyPySpark
def reconcile(spark: SparkSession, src: dict) -> dict:
    pk, cols = src["primary_key"], list(src["columns"])
    lake = current(spark, src).select(*cols).alias("l")
    srcd = source_rows(spark, src).alias("s")
    j = lake.join(srcd, [lake[k] == srcd[k] for k in pk], "full_outer")
    in_lake, in_src = F.col(f"l.{pk[0]}").isNotNull(), F.col(f"s.{pk[0]}").isNotNull()
    same = F.lit(True)
    for c in cols:
        same = same & F.col(f"l.{c}").eqNullSafe(F.col(f"s.{c}"))
    j = j.select(F.coalesce(F.col(f"l.{pk[0]}"), F.col(f"s.{pk[0]}")).alias("key"),
                 F.when(~in_lake, "missing_in_lake").when(~in_src, "extra_in_lake")
                  .when(~same, "different").otherwise("match").alias("result"),
                 *[F.col(f"l.{c}").alias(f"lake_{c}") for c in cols[1:]],
                 *[F.col(f"s.{c}").alias(f"source_{c}") for c in cols[1:]])

Why it exists

Duplicates and late files are visible in the stream. A missing change isn't: keys look fine, counts look fine, and a month-end report is quietly wrong.

In the run

DMS skipped 16 repayment changes on 20 September. Reconciliation found 16 rows that differ; the investigation showed 0 bronze changes in an hour that normally has 10.

Reload, apply as authoritative, check again: 18/18 pass.

On AWS

Run it nightly against an Aurora read replica, never the writer, and alert on hourly change volume per table so a gap pages before a report finds it.

06 · Table design · Iceberg

Partition, sort, compact

The layout is part of the table's definition, not a tuning afterthought, and maintenance runs on a schedule.

src/nexus/silver.py · src/nexus/layout.pyIceberg 1.7
def _create(spark: SparkSession, name: str, df: DataFrame, src: dict) -> None:
    w = df.limit(0).writeTo(name).using("iceberg").tableProperty("format-version", "2")
    layout = src.get("layout")
    if layout:
        col = layout["partition_by"].split("(")[1].rstrip(")")
        w = w.partitionedBy(F.months(col))
    w.create()
    if layout:
        spark.sql(f"ALTER TABLE {name} WRITE ORDERED BY {', '.join(layout['sort_by'])}")

def compact(spark: SparkSession) -> dict:
    """Rewrite the small files MERGE leaves behind into sorted ones, then drop what no snapshot needs."""
    name = "silver.ob_transactions"
    res = spark.sql(f"""CALL {CATALOG}.system.rewrite_data_files(table => '{name}', strategy => 'sort',
                         sort_order => 'customer_id ASC NULLS LAST, booked_at ASC NULLS LAST',
                         options => map('rewrite-all', 'true', 'target-file-size-bytes', '{TARGET_FILE_BYTES}'))""").first()
    return {"rewritten_files": res.rewritten_data_files_count, "added_files": res.added_data_files_count}

What each does

months(booked_at): a hidden partition transform. Queries filter on booked_at; the spec can evolve without rewriting data.

WRITE ORDERED BY customer_id: each file covers a narrow range of customers, so min/max bounds skip files.

rewrite_data_files: MERGE and streaming leave small files; compaction puts them back in order.

Measured here

Per-customer read: 90% less scanned. Monthly report: 77% less. Same answers on every layout.

At Lifepal

The same ideas on Delta (partition pruning, Z-ordering, compaction, AQE) cut the nightly batch from 6 h to 90 min, with the platform at $11k a month against a $19k projection.

06 · Unit cost · AWS

Managing platform cost

Cost is a defect like any other: attributed to a team, visible every week, and fixed where it starts.

infra/finops/cost_by_team.sql · infra/terraform/main.tfAthena over the CUR · Terraform
SELECT resource_tags['user_owning_team']            AS owning_team,
       resource_tags['user_workload']               AS workload,
       product['product_name']                      AS service,
       round(sum(line_item_unblended_cost), 0)      AS spend_90d,
       round(100 * sum(line_item_unblended_cost)
             / sum(sum(line_item_unblended_cost)) OVER (), 1) AS pct
FROM   cur.data_exports
WHERE  line_item_usage_start_date >= current_date - INTERVAL '90' DAY
  AND  product['product_name'] IN ('AWS Glue', 'Amazon Athena', 'Amazon Simple Storage Service',
                                   'AWS Database Migration Service', 'Amazon Relational Database Service')
GROUP BY 1, 2, 3
ORDER BY spend_90d DESC;

resource "aws_athena_workgroup" "audience" {
  for_each = { data_science = 200, finance = 50, dashboards = 20 }   # GB a single query may scan
  name     = each.key
  tags     = merge(local.tags, { workload = each.key })
  configuration {
    enforce_workgroup_configuration    = true
    publish_cloudwatch_metrics_enabled = true
    bytes_scanned_cutoff_per_query     = each.value * 1024 * 1024 * 1024
    result_configuration {
      output_location = "s3://${aws_s3_bucket.lake.bucket}/athena-results/${each.key}/"
    }
  }
}

Four mechanisms

Attribution. Every resource carries an owning team and a workload tag; the Cost and Usage Report, queried in Athena, says who spends what.

Guard-rails. One Athena workgroup per audience with a per-query scan cap, so a careless dashboard can't scan the lake on every refresh.

Right-sized compute. Glue auto-scaling for the hourly apply; FLEX execution for backfills and maintenance.

A budget alert acted on weekly, in the same forum as incidents.

At Lifepal

The platform ran at about $11k a month against a $19k projection. Most of it came from layout (partition pruning, Z-ordering, compaction) and from refreshing data only as often as people need it.

07 · Data Science · Spark SQL

A feature as it was known at decision time

Open Banking enrichment changes rows after the fetch. The change history in silver lets a feature see exactly what the model saw.

src/nexus/gold.pySpark SQL · Iceberg
        pit AS (
          SELECT a.application_id, sum(h.amount) AS income_90d
          FROM apps a JOIN {table('silver', 'ob_transactions_history')} h
            ON h.customer_id = a.customer_id AND h.booked_at >= a.decided_at - INTERVAL 90 DAYS
           AND h.booked_at < a.decided_at AND h.fetched_at <= a.decided_at
           AND h.valid_from <= a.decided_at AND a.decided_at < h.valid_to AND NOT h.is_deleted
          WHERE h.category = 'salary' GROUP BY 1),
        naive AS (
          SELECT a.application_id, sum(t.amount) AS income_90d
          FROM apps a JOIN {table('silver', 'ob_transactions')} t
            ON t.customer_id = a.customer_id AND t.booked_at >= a.decided_at - INTERVAL 90 DAYS
           AND t.booked_at < a.decided_at
          WHERE NOT t.is_deleted AND t.category = 'salary' GROUP BY 1)

The trap

A join on today's rows uses today's categories. Salary credits relabelled after the decision inflate income the model never saw, so offline results look better than production.

In the run

The naive feature differs for 72 of 111 decisions since 1 July, by £2,807 of income on average.

At Lifepal

Feature pipelines behind the customer-risk and claims-fraud models (LightGBM, XGBoost): point-in-time training sets, training/serving parity, drift monitoring and recalibration.
